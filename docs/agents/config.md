# Config Reference

All fields in `config.json` (`~/.autoAnimeDownloader/config.json` on Linux, `%APPDATA%\.autoAnimeDownloader\config.json` on Windows).

Struct defined in `src/internal/files/filemanager.go`. Defaults set in `DefaultConfig()`.

## Fields

| Field | JSON key | Type | Default | Description |
|-------|----------|------|---------|-------------|
| `CompletedAnimePath` | `completed_anime_path` | `string` | `~/Animes` (`""` if the home dir is unknown) | The Jellyfin library location. Completed episodes are **hardlinked** here (not moved/copied). **Required**. The download/seeding working directory (rain's DataDir) is **derived** from it — see "Download Path" below — so there is no separate path to configure |
| `AnilistUsernames` | `anilist_usernames` | `[]string` | `[]` | Anilist usernames to sync watch lists from (multi-account supported). **Optional** — an installation can run entirely on standalone animes (`standalone_animes`, see [decisions/049](decisions/049-standalone-anime-tracked-by-the-list-is-the.md)) |
| `MALUsernames` | `mal_usernames` | `[]string` | `[]` | MyAnimeList usernames, used as **list sources only**: each MAL account answers which anime, in which status, with what progress — identity, episodes and metadata still come from AniList, reached through `idMal` ([decisions/095](decisions/095-myanimelist-is-a-list-source-not-a-metadata-source.md)). The list must be **public** (read from the unofficial `load.json`, no client ID). `ExcludedLists` doesn't apply (MAL has no custom lists). Status mapping: watching→`CURRENT`, completed→`COMPLETED`, on hold→`PAUSED`, dropped→`DROPPED`, plan to watch→`PLANNING`, rewatching flag→`REPEATING`; `DownloadStatuses`/`DeleteStatuses` apply to it with the same OR/AND rules. **Optional**, not validated |
| `AnilistUsername` | `anilist_username` | `string` | `""` | **Legacy.** Single-username field, `omitempty`. Migrated into `AnilistUsernames` and cleared by `FileManager.LoadConfigs()` (`filemanager.go`) — **only there**, and the migration persists. `handleUpdateConfig` deliberately does **not** repeat it: a PUT still carrying the singular key is saved and cured on the next load (decisions/090). Kept only for backward compatibility |
| `CheckInterval` | `check_interval` | `int` | `10` | Minutes between verification loops. Must be > 0 |
| `RecentShelfDays` | `recent_shelf_days` | `int` | `3` | Days a downloaded, still-unwatched episode stays on the Status page's Recents shelf (`GET /animes`' `recent`). `0` turns the shelf off; 0..30, anything else is a 400 ([decisions/151](decisions/151-the-recents-shelf-is-derived-in-get-animes-after.md)) |
| `MaxEpisodesPerAnime` | `max_episodes_per_anime` | `int` | `12` | Max saved episodes per anime before oldest are deleted, and the width of the pack-selection window (`daemon.windowEnd`). `0` = off — no ceiling, no window end (`daemon.effectiveMax`/`windowEnd`). **Applies only to the episode-by-episode path** — never to a batch download (a batch is one torrent, so limiting records would limit neither bytes nor library files; see [decisions/048](decisions/048-max-episodes-per-anime-never-limited-batches-the.md)). Must be >= 0 |
| `MaxBatchTorrentSizeGB` | `max_batch_torrent_size_gb` | `float64` | `100` | The **only** guard on batch eligibility — packs are no longer gated by anime metadata (finished/episode count), just by what the search actually returns. Ceiling in **GiB** per batch torrent: results above it are dropped from the Nyaa search result (`daemon.filterBySize`), not downloaded and deleted. Also pushed into the nyaa package by `LoadConfigs` (`ApplyNyaaSettings` → `nyaa.SetMaxBatchTorrentSizeGB`), where an oversized pack row is dropped **before** it counts toward the pagination floor — otherwise three giant packs on page 1 end the page descent ahead of the partial packs that fit (see [Decisions #80](decisions/080-the-pack-size-ceiling-is-applied-twice-in-the-nyaa.md)). `100` fits a full 1080p season pack but not a full One Piece pack (for a long-running series what passes is a partial pack, covering the selection window). `0` = off. A torrent whose size failed to parse (`Size == 0`) passes the filter. Must be >= 0. **Release note:** an installation that already has `max_batch_torrent_size_gb: 0` saved keeps the filter off — `LoadConfigs` unmarshals over the new default, so an explicit `0` on disk is not overwritten and must be raised by hand. With `max_episodes_per_anime = 0` the window is fully open and a series like One Piece can resolve ~14 packs in a single pass, throttled only by `max_batch_torrent_size_gb` (per torrent) and `checkRootBudgetSpace` |
| `MaxEpisodeTorrentSizeGB` | `max_episode_torrent_size_gb` | `float64` | `5` | Same, for the single-episode / multi-episode / movie searches. `5` passes a WEB-DL (~1.4 GB) and a competent BD encode (~2 GB) and blocks a BDRemux (~6-8 GB) — an episode had no ceiling at all until this default existed (the field was absent from `DefaultConfig()`, and `0` = unlimited is a valid zero value, so the gap was invisible). `0` = off. Must be >= 0 |
| `MinSeeders` | `min_seeders` | `int` | `3` | Floor on the seeders column: results below it are dropped from every Nyaa search (`daemon.filterBySeeders`, applied by `filterSearchResults` alongside the size ceiling). `0` = off — with no floor a 0-peer result is a valid candidate and gets picked whenever it is the only one (measured: `[DB] Naruto Shippuuden Movie 3` was the sole candidate for episode 3, at 0 peers). Unlike the size ceiling, an unparseable seeders column counts as `0` and is **discarded** — see [decisions/054](decisions/054-seeders-floor-unreadable-seeders-are-discarded.md). The default is `3` and not `1` because `1` blocks only the literally dead torrent, and a single seeder stalls often. Must be >= 0. Ranking among survivors uses `healthTier` bands with floors 10 and 50 seeders (not a config field; see [decisions/107](decisions/107-source-ranks-finished-series-empty-source-is-web.md)) |
| `MaxSearchPages` | `max_search_pages` | `int` | `5` | Ceiling on Nyaa result pages **per search**. Not a fixed cost: a search reads page 1 and only goes deeper while it has fewer than 3 accepted candidates, and stops early on an empty page (`nyaa.fetchSearchPages`). Page 2 used to be fetched unconditionally, so a search that resolves on page 1 now costs **one** fetch instead of two — that saving is what pays for the higher ceiling. `<= 1` = page 1 only. Applies to all three searches (episode, anime — which covers both packs and episodes, movie); movie reads a single page before. Pushed into the nyaa package by `LoadConfigs` (`ApplyNyaaSettings`), like `priorities`. Must be >= 0 |
| `NyaaRequestDelaySeconds` | `nyaa_request_delay_seconds` | `float64` | `0` | Minimum gap, in seconds, between two Nyaa HTML requests: search pages and torrent detail pages alike, since both go through `nyaa.fetchNyaaPage`. The gap is **global**, not per search: the pass searches several animes at once and they queue for one slot (`nyaa/pacing.go`, [decisions/135](decisions/135-the-nyaa-request-gap-is-one-global-slot-held.md)). The first request, or one made after the gap has passed, goes out at once. A pass takes roughly `gap × requests` longer. `0` = off, the default (no wait, no lock). Pushed into the nyaa package by `LoadConfigs` (`ApplyNyaaSettings`), like `max_search_pages`, so a save applies it to the next request. Must be >= 0 |
| `MinFreeDiskGB` | `min_free_disk_gb` | `int` | `10` | Slack kept on the library volume, in **GiB** (2^30). A new torrent is refused when `free - reserved` would fall below this (`daemon.checkRootBudgetSpace`, applied in `attemptDownloadWithRetries` and `addAndPrioritize`). The check subtracts the announced torrent size and what the queue still has to write first ([decisions/101](decisions/101-the-disk-guard-counts-what-the-queue-still-has-to.md)). The verification pass still runs in full — pruning and organizing are what free space. `0` = off **for the floor only**: a torrent bigger than `free - reserved` is still refused ([decisions/093](decisions/093-the-disk-guard-has-two-triggers-and-the-size-one.md)). Must be >= 0. Replaces `min_free_disk_percent` (unknown JSON key, dropped on load — no migration). Also drives `disk_low` in `GET /status`, which is this add-gate for a torrent of size 0. With `download_roots` it is each root's limit unless the root sets its own `min_free_gb` ([decisions/154](decisions/154-several-download-roots-each-placement-records-its.md)) |
| `EpisodeRetryLimit` | `episode_retry_limit` | `int` | `5` | Max magnet links to try per episode before giving up. Must be >= 1: 0 tried none, so no episode downloaded one by one; a 0 saved by an older version becomes 1 when the config loads (`LoadConfigs`) |
| `MaxConcurrentDownloads` | `max_concurrent_downloads` | `int` | `3` | With `torrent_client: "qbittorrent"` it becomes qBittorrent's `max_active_downloads` only when `qbittorrent_manage_settings` is on; otherwise qBittorrent's own queue applies and this is ignored ([decisions/144](decisions/144-with-qbittorrent-the-apps-torrents-never-have-a.md)). How many **incomplete** torrents may run at once; the rest wait in the download queue (`torrents/queue.go`, status slug `queued`). `0` = no limit. Seeding is never limited. Must be >= 0. Applied by `SetMaxActiveDownloads` from three places: boot (`cmd/daemon/main.go`), `PUT /config`, and the top of every `AnimeVerification`. No migration needed — `LoadConfigs` unmarshals **over** `DefaultConfig()`, so a `config.json` written before this field loads with the default already in place |
| `DeleteWatchedEpisodes` | `delete_watched_episodes` | `bool` | `true` | Whether to auto-delete episodes marked as watched on Anilist |
| `WatchedEpisodesToKeep` | `watched_episodes_to_keep` | `int` | `2` | Number of watched episodes to keep before deleting. `0` = delete all watched. The default is `2` because `DeleteWatchedEpisodes` ships **on**: with no slack the episode disappears the moment it is marked, which forgives neither "marked it by mistake" nor "wanted to rewatch". Must be >= 0 |
| `ExcludedLists` | `excluded_lists` | `[]string` | `[]` | Names of Anilist custom lists to exclude from downloads. AniList accounts only — MyAnimeList has no custom lists |
| `ExcludedList` | `excluded_list` | `string` | `""` | **Legacy.** Same migration pattern as `AnilistUsername` — merged (comma-split) into `ExcludedLists` by `FileManager.LoadConfigs()` on load |
| `DisableSeeding` | `disable_seeding` | `bool` | `false` | With `torrent_client: "qbittorrent"` it means **almost no upload**: each torrent is held at `qbittorrent_disable_seeding_upload_kib` while it downloads and released once organized, since qBittorrent can't refuse uploads ([decisions/144](decisions/144-with-qbittorrent-the-apps-torrents-never-have-a.md)). With the built-in client, no upload at all: the torrent session never unchokes a peer and serves no allowed-fast piece, even during the download, and every torrent is removed with its download copy as soon as it is organized into the library (the hardlink stays). A pack's parts that were not linked (another season, extras) are deleted with it. Downloads may be slower, since peers favor whoever uploads back. Toggling rebuilds the session: right away from `PUT /config` (only when the value changed), and the pass re-applies it every cycle. Turning it on also releases the torrents already seeding, on the next pass. See [decisions/119](decisions/119-disable-seeding-means-no-upload-at-all-and-a.md) |
| `RenameFilesForJellyfin` | `rename_files_for_jellyfin` | `bool` | `false` | Give the **library hardlink** a Jellyfin-compatible name (`"Anime Name - E05.mkv"`). Single episodes use the episode number from the record (only when the torrent holds one video file); **batch packs** rename each file using the number parsed out of its own filename, so pack episodes mix into the anime folder alongside individually downloaded ones. Files with no readable number (NCOP/NCED, extras, movies) keep the raw name. The seeded copy in the download directory is never renamed (that would break seeding). In **direct mode** the name is decided before the add and becomes the torrent's own file name: a single episode becomes `"Series - S02E05.mkv"` (numbered per `episode_numbering`); packs and movies keep their raw names |
| `LibraryMode` | `library_mode` | `string` | `"hardlink"` | How torrents reach the library. `"hardlink"` (also what an empty value means) is everything else on this page: download into `.torrents`, hardlink into the library. `"direct"` writes each torrent **straight to its final path** and seeds it from there — no `.torrents` copy, no hardlink, so filesystems without hardlinks work. See [Direct Library Mode](#direct-library-mode). Applies to torrents **added** while it is on; a torrent keeps the mode it was added in. Changing it rebuilds the torrent session (like `disable_seeding`). Must be one of the two values |
| `AutoDeleteDownloads` | `auto_delete_downloads` | `bool` | `false` | For torrents added in direct mode. `false` = **keep forever**: no automatic path (watched pruning, `delete_statuses`, blacklist, off-list, the episode limit) deletes a direct-mode torrent — **whatever `library_mode` is now**, so switching back to hardlink mode doesn't start deleting them — and while direct mode is on, `max_episodes_per_anime` is ignored (every aired episode downloads, the pack window is open — `daemon.effectiveMax`/`windowEnd`). `true` = the usual rules apply, and deleting a file also stops seeding it. Torrents added in hardlink mode always follow the usual rules. Manual deletes always work |
| `IncompleteFiles` | `incomplete_files` | `string` | `"part"` | Direct mode only. `"part"` writes `<name>.part` while the torrent downloads; organize renames to the final name (stopping the torrent for the rename and starting it again), so a media server never scans a half-written episode. `"in_place"` writes the final name from the start. Fixed per torrent when it is added. Must be one of the two values |
| `IncompletePath` | `incomplete_path` | `string` | `""` | Direct mode only; hardlink mode ignores it. An **existing** folder on a fast drive (SSD/NVMe) where torrents download before their files move into the library, so a library on a slow or SMR disk only takes one sequential write per file. Files there live in `<incomplete_path>/<infohash>/<library-relative path>` under their real names (never `.part`, whatever `incomplete_files` says). On completion organize copies them into the library while the torrent keeps seeding, then switches the torrent over in a short stop ([decisions/141](decisions/141-staged-downloads-are-copied-into-the-library-while.md)). With `torrent_client: "qbittorrent"` the folder is each torrent's qBittorrent download path: qBittorrent moves the finished torrent in itself (not seeding during the move), with a path map the folder must be under an `app` entry, and a redownload of missing files writes into the library directly ([decisions/145](decisions/145-with-qbittorrent-a-staged-torrent-downloads-into.md)). Frozen per torrent when it is added: changing or clearing it only affects new torrents. Pick a folder **inside** the fast drive, not its mount point: an unmounted mount point still looks like an existing folder. The app never creates this folder; on save it must exist, be writable and sit outside the library (`files.ProbeIncompleteFolder`), and a pass that finds it gone stops with the `incomplete_folder` code. `""` = off |
| `DownloadRoots` | `download_roots` | `[]DownloadRoot` | `[]` | Direct mode only. Several download folders, `{"name": "ssd", "path": "/mnt/ssd/Anime", "min_free_gb": 200}`, in fill order, the first the highest priority (`Config.Roots`). The order only steers new torrents: a placed torrent keeps its root, so reordering moves no file. A new torrent goes to the anime's own folder (`AnimeSettings.Root`), else the one already holding its series, else the first in the list with room. A folder has room until its drive would keep less than its `min_free_gb` (`Config.RootMinFreeGB`; absent = `min_free_disk_gb`), so it fills up to that and the next one takes over; none with room refuses the torrent. Roots on one drive share its free space. Empty = one root, `completed_anime_path`, named `library`; once the list has any, `completed_anime_path` is a download folder only if listed. A placement in the library stores no root path ([decisions/154](decisions/154-several-download-roots-each-placement-records-its.md)) |
| `IncompleteMinFreeDiskGB` | `incomplete_min_free_disk_gb` | `int` | `10` | `min_free_disk_gb` for the `incomplete_path` drive, in GiB. Only checked when that folder is on another filesystem than the library (`daemon.checkRootBudgetSpace`). Must be >= 0. On a download root's own drive, that root's limit applies instead, counting the other roots' staging downloads ([decisions/154](decisions/154-several-download-roots-each-placement-records-its.md)) |
| `TorrentClient` | `torrent_client` | `string` | `"builtin"` | Which BitTorrent client the daemon drives. `"builtin"` (also what an empty value means) is the embedded rain session; `"qbittorrent"` drives an external qBittorrent 5.0+ (Web API 2.11+) through its WebUI (`torrents.QBitBackend`, [decisions/142](decisions/142-qbittorrent-stops-each-placed-torrent-at-its.md)). **Read once at startup** (`cmd/daemon` `newTorrentBackend`): `PUT /config` answers `restart_required: true` when it changed. With `"qbittorrent"`, `library_mode` must be `"direct"`; `incomplete_path` is qBittorrent's per-torrent download path (decisions/145); `max_concurrent_downloads` applies only with `qbittorrent_manage_settings`, and `disable_seeding` is an upload limit (decisions/144). Must be one of the two values |
| `QBittorrentURL` | `qbittorrent_url` | `string` | `""` | qBittorrent's WebUI address (`http://127.0.0.1:8080`; a base path behind a reverse proxy is kept). Required with `"qbittorrent"`, an http(s) URL. Read on every `Ensure`, so a change applies on the next pass. With qBittorrent in Docker, publish its WebUI on the same port inside and out (`-p 8080:8080`, with its WebUI on 8080 inside the container): its Host header validation refuses a port mismatch with 401, which looks like a wrong password ([decisions/142](decisions/142-qbittorrent-stops-each-placed-torrent-at-its.md)). The key existed before rain and came back with this backend; an old config that still carries it stays on the built-in client |
| `QBittorrentUsername` | `qbittorrent_username` | `string` | `""` | WebUI login, unless an API key is set. Pseudonymized in bug reports |
| `QBittorrentPassword` | `qbittorrent_password` | `string` | `""` | WebUI password. A **secret**: `GET /config` answers `"__saved__"` (`files.SecretPlaceholder`) instead, and a `PUT` that sends the placeholder keeps the saved value ([decisions/143](decisions/143-the-qbittorrent-password-and-api-key-come-back.md)); redacted in bug reports |
| `QBittorrentAPIKey` | `qbittorrent_api_key` | `string` | `""` | qBittorrent API key (Web API 2.14.1+, made in its WebUI), sent as `Authorization: Bearer`; used instead of the user and password when set. A secret, like the password |
| `QBittorrentCategory` | `qbittorrent_category` | `string` | `"autoanimedownloader"` | Category every torrent of the app gets; created on connect. The backend only lists, controls and deletes torrents in it, so a qBittorrent shared with other uses is left alone. Empty falls back to the default |
| `QBittorrentPathMap` | `qbittorrent_path_map` | `[]PathMapping` | `[]` | `[{"app": "/mnt/anime", "qbittorrent": "/downloads"}]`: the same folder as each side sees it, when qBittorrent runs in Docker or on another machine. Every path sent to qBittorrent and read back goes through the longest matching prefix. Both sides absolute, no folder twice or nested on one side, and `completed_anime_path` must fall under an `app` entry when the map isn't empty. Empty = identical paths |
| `QBittorrentManageSettings` | `qbittorrent_manage_settings` | `bool` | `false` | "Let the app manage this qBittorrent's settings": the app sets qBittorrent's global settings it relies on. For now that is the download queue: queueing on, `max_active_downloads` from `max_concurrent_downloads` (`0` → `-1`, no limit), and `max_active_uploads` and `max_active_torrents` at `-1`, so seeding is never capped. It also turns off qBittorrent's ".!qB" extension (the app names incomplete files itself) and moves `disk_io_type` from Default or memory-mapped to "Simple pread/pwrite", once per connection; that one applies when qBittorrent restarts. Read on every `Ensure`, and only the keys that differ are written, so a queue changed in qBittorrent's WebUI comes back on the next pass. Off (the default, for a qBittorrent also used for other things) the app changes nothing global, and the connection test reports qBittorrent's own queue. Per-torrent limits (no share limit, the `disable_seeding` floor) apply either way ([decisions/144](decisions/144-with-qbittorrent-the-apps-torrents-never-have-a.md)) |
| `KeepRemovedReleaseCards` | `keep_removed_release_cards` | `bool` | `true` | The anime page's Torrents section keeps the card of a torrent that is gone (pruned, deleted), marked removed, from `releases.json`. Off hides those cards; the records stay, so turning it back on brings them back ([decisions/150](decisions/150-what-a-torrent-was-is-recorded-once-per-info-hash.md)) |
| `QBittorrentDisableSeedingUploadKiB` | `qbittorrent_disable_seeding_upload_kib` | `int` | `16` | `disable_seeding`'s upload limit per torrent with qBittorrent, in KiB/s. Not smaller by default because the limit also carries the download's own requests: a download runs at most a few hundred times it (measured: 1 KiB/s took 5x longer on a 7 MiB pack, 1 B/s never got the file list). Must be >= 1 with `"qbittorrent"` while `disable_seeding` is on (0 is unlimited there); a missing value reads as 0 in a `PUT`. Re-applied to every torrent of the app on each poll; a change applies at once from `PUT /config` |
| `ShokoEnabled` | `shoko_enabled` | `bool` | `false` | Episodes already in the user's Shoko library are not searched or downloaded one by one, take no slot of `max_episodes_per_anime`, count as there in the progress bars, and show as **In Shoko** on the anime page; the app never deletes Shoko's files. A pack chosen for other episodes still brings their files until per-file selection lands; `shoko_full_packs` (or the anime's own choice) says whether the app records or removes them (the Shoko spec, [decisions/147](decisions/147-episodes-already-in-shoko-leave-the-list-both.md)). Can be on only once signed in (`shoko_url` and `shoko_api_key` set). Off: nothing below is read |
| `ShokoURL` | `shoko_url` | `string` | `""` | Shoko Server's address (`http://127.0.0.1:8111`). Set by the sign-in (`POST /shoko/login`, trailing slash trimmed); changing it by hand with the key still saved is refused (sign in again). Emptied, it signs out: the saved key is cleared with it |
| `ShokoAPIKey` | `shoko_api_key` | `string` | `""` | The key Shoko gave the app at sign-in (device `AutoAnimeDownloader`); the password is never saved. A **secret**, like the qBittorrent password: `GET /config` answers `"__saved__"`, a `PUT` with the placeholder keeps it only for the same `shoko_url` ([decisions/143](decisions/143-the-qbittorrent-password-and-api-key-come-back.md)), redacted in bug reports |
| `ShokoRefreshHours` | `shoko_refresh_hours` | `int` | `24` | How often the pass reads what is new in Shoko. The first sync (and a full resync, `POST /shoko/sync {"full":true}`) reads every series and the owned episodes of the series that match a followed anime; later ones only the files imported since the newest seen (`internal/shoko`). Must be >= 1 while Shoko is on; a missing or 0 value reads as 24 |
| `ShokoWatch` | `shoko_watch` | `bool` | `true` | Follow Shoko's changes as they happen: the daemon holds a connection to Shoko's event hub (SignalR, the `shoko` feed), and a file linked to an episode or deleted refreshes that series about 10 s after the events settle, then the anime page; the next pass downloads an episode deleted there. After every (re)connection it catches up: the newer-only sync, then every followed series read again, which sees a deletion or an unlink made while it was away. An unlink while connected sends no event and waits for the next reconnection or full resync (`shoko_full_resync_days`). `shoko_refresh_hours` stays newer-only (files imported while nothing listened). Read before every connection and every 30 s during one (turning it off closes the connection); reconnects with a backoff of 5 s to 5 min ([decisions/148](decisions/148-shokos-change-events-refresh-only-the-series-they.md)) |
| `ShokoFullResyncDays` | `shoko_full_resync_days` | `int` | `30` | Read all of Shoko again every that many days, on the pass that finds it due (`Store.FullDue`): the one way, besides the Full resync button, to see a file unlinked from an episode while connected, which Shoko never announces. `0` = never on its own. Must be >= 0 ([decisions/148](decisions/148-shokos-change-events-refresh-only-the-series-they.md)) |
| `ShokoFullPacks` | `shoko_full_packs` | `bool` | `true` | "Download Full Megapacks", for the whole list; an anime overrides it (`AnimeSettings.ShokoPackEpisodes`, `Config.KeepsShokoPackEpisodes`). A pack chosen for the missing episodes downloads whole and so brings the episodes in Shoko it covers. On, the second selection records those too (only from a pack of known range), so they show as downloaded and follow the app's rules ([decisions/149](decisions/149-a-pack-chosen-for-the-missing-episodes-records-the.md)); in direct mode with `auto_delete_downloads` off that costs nothing, and with it on an unwatched one takes a slot of `max_episodes_per_anime` from the next pass on. Off, they are removed: each check skips their files (qBittorrent priority 0) and deletes the ones already downloaded once the pack finished; a rain pack then leaves the client, the rest kept, since rain can't skip a file or seed with one missing. A pack downloaded into one of Shoko's import folders (`shoko_path_map`) is only skipped: what was written there is Shoko's. Only files the pack window maps to an episode (the anime's episode total known) and episodes the app has no record of ([decisions/153](decisions/153-a-packs-episodes-already-in-shoko-are-removed-for.md)) |
| `ShokoPathMap` | `shoko_path_map` | `[]ShokoPathMapping` | `[]` | `[{"app": "/mnt/shoko-drop", "shoko": "/import"}]`: the same folder as the app and as Shoko see it, when one of them runs in Docker or on another machine. The app reads Shoko's import folders (with each sync, kept in `shoko.json`) and never manages them: a download folder is **in Shoko** when, translated through the longest matching prefix (`Config.ShokoPath`; no match keeps the path), it is one of them or lies inside one (`ShokoService.ShokoFolder`). Read only while Shoko is on, in direct mode. A torrent that finishes in such a folder: organize marks the records `handed_to_shoko`, the torrent keeps seeding, and Shoko is asked to import new files (`GET /api/v3/Action/ImportNewFiles`, one request for the downloads that finish together, sent again by the next pass if it failed). A handed-off torrent whose files Shoko moved leaves the client, files kept. Deleting a handed-off episode drops its record, never its file. Any other download folder is an ordinary one. While a download folder is in Shoko: `incomplete_files: "part"` or an `incomplete_path` (with qBittorrent, `"part"` and no `incomplete_path`: it moves a staged torrent in under its final names), so Shoko never sees a half-written file. ## Download Path

There is no `save_path` field. The download/seeding working directory is **derived** from `completed_anime_path` at every use, via `Config.DownloadPath()` (`internal/files/filemanager.go`):

```
<completed_anime_path>/.torrents
```

Torrents download and keep seeding there (rain's `DataDir`, layout `<DownloadPath()>/<torrent-id>/...`); on completion, video files are hardlinked out into `completed_anime_path` itself (the Jellyfin library). Because the download directory is a subfolder of the library, the two are guaranteed to share a filesystem — the old "must be on the same volume" requirement is now an architectural invariant rather than something the user can misconfigure. `Librarian.ProbePath(completed_anime_path)` still runs (on config save and on every verification pass) to catch filesystems that don't support hardlinks at all (exFAT/FAT32, some SMB shares), unrelated to the cross-volume case.

**No automatic migration.** `daemon.MigrateSavePath` used to move a legacy `save_path`'s torrent
folders into the derived download path at boot; it was **removed** along with the `SavePath` field.
A `config.json` that still carries `save_path` loads fine (JSON ignores unknown fields) and the key
disappears on the next save, but its data is **not** moved — rain opens the derived path, finds it
empty and re-downloads. Moving the folder is now a manual, pre-upgrade step. See decisions/031.

## Direct Library Mode

With `library_mode: "direct"` there is no download copy: rain writes each torrent through a custom
storage (`torrents/placement.go`) straight to where it lives in the library, and seeds from there.
Design: [the spec](../superpowers/specs/2026-11-22-direct-library-mode-design.md); the rules that
look odd: [decisions/136](decisions/136-direct-mode-places-a-torrent-before-the-add-and.md),
[decisions/137](decisions/137-direct-mode-deletes-through-the-torrent-and-keep.md).

| Torrent | Path |
|---|---|
| Single episode | `<completed_anime_path>/<Series>/Season NN/<file>` |
| Movie (AniList format `MOVIE`) | `<completed_anime_path>/<Series>/Specials/<file>` |
| Pack (any multi-episode torrent) | `<completed_anime_path>/<Series>/<the torrent's own folders>` |

`<Series>` is the title of the PREQUEL chain's root (the first season), so every season lands in one
folder; with the chain unknown it is the anime's own title. Once a series has a folder, later
seasons reuse it even if AniList renamed the root since. `NN` follows the chain: an entry's own
season marker, else its prequel's season for a later part ("Part 2", "Cour 2"), else the next
season ([decisions/138](decisions/138-direct-mode-numbers-seasons-along-the-tv-prequel.md)). `tvshow.nfo` goes in the series
folder with the root's AniList id. A destination that already exists on disk (or belongs to another
torrent) gets the torrent's short hash appended instead of being overwritten.

The placement is decided and saved (`placements.json`, next to `session.db`) **before** the add,
and the file map is frozen when rain first prepares the torrent: changing a setting, the mode or an
AniList title later never moves a file that is seeding. Its paths are stored **relative to the
library**, so moving the library and re-pointing `completed_anime_path` at it keeps everything
seeding. Torrents added in hardlink mode keep downloading and seeding in `.torrents` after the
switch.

Deleting: from the app (web UI or CLI), a direct-mode episode's torrent is removed with its files
(and the folders they leave empty). A file deleted by hand, outside the app (from Jellyfin, a file
manager), is **not** downloaded again on its own: its torrent stays stopped and its row in Downloads
shows a quiet "File not found" note, nothing else
([decisions/139](decisions/139-a-direct-mode-file-deleted-outside-the-app-is.md)). To get such
files back (a replaced library folder above all), "Redownload missing files" above the Downloads
list (CLI `torrents redownload-missing`) fetches them again into the same paths, for the torrents
the user leaves ticked
([decisions/140](decisions/140-redownloading-missing-files-adds-the-same-torrent.md)). A failed
download whose episode was then fetched from another release leaves no garbage: the end-of-pass
sweep deletes files no torrent and no episode record points at any more.

`completed_anime_path` is still required and still the library root; `Config.DownloadPath()` still
exists (it is where torrents added in hardlink mode live). Validation and the per-pass probe check
that the folder is **writable** (`files.ProbeWritable`) instead of probing hardlinks.

## Removed Field

`qbittorrent_url` was **removed** when the external qBittorrent dependency was replaced by an embedded BitTorrent client, and **came back** with the optional qBittorrent backend (`torrent_client`, above). Its old `QBITTORRENT_URL` env override of the running daemon did not come back; `QBITTORRENT_URL` is now read only by `docker/entrypoint.sh`, when it writes the first `config.json` ([environment.md](environment.md#docker-entrypoint-initial-configjson)). An old config that still carries the key loads it, but stays on the built-in client: only `torrent_client: "qbittorrent"` selects qBittorrent.

`save_path` was **removed** entirely — first as a user-configurable field (the download directory is derived, see "Download Path" above), then as a struct field once the migration that read it was deleted. Old configs carrying the key load fine and the key disappears on the next save.

## Required Fields

Daemon checks these in `isConfigComplete()` (`daemon/helpers.go`) before starting the verification loop:
- `completed_anime_path` — **the only one.** An AniList account is *not* required: with standalone animes the app works with no list at all, and demanding an account would strand that installation on the config screen

If missing, daemon opens browser to `http://localhost:<port>/#/config?missingConfig=true`.

Default: `completed_anime_path` starts as `~/Animes` (`DefaultConfig()`), so a fresh install is already "complete". On the **first boot only** (no `config.json` yet — `FileManager.ConfigExists()`, checked in `main()` before the first `LoadConfigs()`) the daemon opens `http://localhost:<port>/#/status`.

## Validation (API)

`handleUpdateConfig()` in `endpoint_config.go` validates:
- `completed_anime_path` — non-empty. `anilist_usernames` is **not** validated (see Required Fields); the legacy `anilist_username` is migrated into it by `LoadConfigs`, not by this handler (decisions/090)
- `completed_anime_path` must support hardlinks — verified with a single-path probe (`Librarian.ProbePath`); a filesystem without hardlink support is rejected with HTTP 400. In direct mode it only has to be writable (`files.ProbeWritable`)
- `library_mode` — `""`, `"hardlink"` or `"direct"`; `incomplete_files` — `""`, `"part"` or `"in_place"`; `episode_numbering` — `""`, `"season"` or `"entry"` (an empty value means the default)
- `check_interval` — > 0
- `episode_retry_limit` — >= 1
- `watched_episodes_to_keep`, `max_concurrent_downloads`, `max_episodes_per_anime`, `max_batch_torrent_size_gb`, `max_episode_torrent_size_gb`, `min_seeders`, `max_search_pages`, `nyaa_request_delay_seconds` — >= 0 (`max_episodes_per_anime` and `max_batch_torrent_size_gb` treat `0` as "off"; see their field descriptions above)
- `min_free_disk_gb`, `incomplete_min_free_disk_gb` — >= 0
- `download_roots` — direct mode only: names unique and not empty, `min_free_gb` 0 or more, paths absolute, distinct, not inside one another, existing (never created) and writable (`validateDownloadRoots`)
- `incomplete_path` — direct mode only, when set: absolute, an existing writable folder (never created), outside the library and not containing it (`files.ProbeIncompleteFolder`)
- `shoko_enabled` — on only with `shoko_url` and `shoko_api_key` set (sign in first), and then `shoko_refresh_hours` >= 1 (`validateShoko`); `shoko_path_map` as `qbittorrent_path_map` (`validateShokoPathMap`); with a download folder in one of Shoko's import folders as last read (direct mode), `incomplete_files: "in_place"` needs an `incomplete_path`, and qBittorrent takes no `incomplete_path`
- `torrent_client` — `""`, `"builtin"` or `"qbittorrent"` (`validateTorrentClient`). With `"qbittorrent"`: `library_mode` `"direct"`, `qbittorrent_disable_seeding_upload_kib` >= 1 when `disable_seeding` is on, `qbittorrent_url` an http(s) URL, and `completed_anime_path` (and `incomplete_path`, when set) under an `app` folder of `qbittorrent_path_map` when the map isn't empty. The map itself (whatever the client): both sides absolute, no folder twice or nested on one side (`validatePathMap`). A secret sent as `"__saved__"` keeps the saved value, before any of this runs (decisions/143)

## Webhook Events

The values of `notifications.webhooks[].events`. The web UI groups them as Episodes, Library and
System; a new message preset starts with the episode events plus the system ones.

| Event | Group | Fires when |
|-------|-------|------------|
| `new_episode` | Episodes | a torrent for a new episode was found and is being added |
| `download_failed` | Episodes | a real failure: every candidate refused by the torrent client (`{{reason}}` = `torrent rejected`) or the torrent dropped for an error or stalling (`{{reason}}` = its error). Once per (episode, torrent); a different torrent failing is sent again. **Not** a missing torrent (that is `episode_stuck`) nor a full disk (`disk_low`) |
| `download_completed` | Episodes | an episode was organized into the library |
| `episode_deleted` | Episodes | episodes were removed from the library |
| `episode_limit_reached` | Library | an anime hit `max_episodes_per_anime` (N downloaded, M waiting for you to watch); once until it drops below the limit |
| `episode_stuck` | Library | an episode has gone 48 h without downloading since its first problem (empty search, everything above the size limit, no seeders, add refused, disk full, or its torrent dropped for stalling/failing), while that problem is still recent. | `season_complete` | Library | a finished anime (AniList status `FINISHED`) has every episode you haven't watched in the library; once per anime, ever |
| `unwatched_backlog` | Library | the next episode to watch (progress + 1) has been in the library for 30 days; says how many unwatched episodes and how much space they take. Once per anime and progress — watching one and stopping again restarts the 30 days from that episode's download date |
| `leftover_files` | Library | weekly digest, while files you are done with are still in the library after the check's own cleanup: episodes at or below progress − `watched_episodes_to_keep`, and animes that left every download status. One line per anime with its size; the title carries the total of the lines that webhook gets (a webhook filtered by account counts only its animes). Skipped on a check where some list account failed to answer |
| `library_missing` | System | the library folder vanished or was replaced (unmounted drive); everything in it will be downloaded again — except torrents added in direct mode, which stop and show their files missing until the user picks "Redownload missing files" ([decisions/139](decisions/139-a-direct-mode-file-deleted-outside-the-app-is.md)) |
| `check_failing` | System | checks have aborted for ≥ 30 min and ≥ 2 passes in a row (setup incomplete doesn't count); once per run of failures, and again with `{{reason}}` = `recovered` on the first pass that finishes. `{{reason}}` is otherwise the pass error code |

which also reach a webhook filtered by `anime_sources` — they are not about any account's anime.

## Loading Behavior

`LoadConfigs()` starts from `DefaultConfig()`, then unmarshals `config.json` on top. Fields missing from JSON keep their defaults. If file is empty, corrupt, or missing, defaults are written to disk.
